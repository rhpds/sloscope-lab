= Understand the reliability terms and architecture

Before you run anything, follow the path from a customer concern to measured evidence and a reviewed recommendation. You do not need to become an SRE specialist to use the rest of the lab.

== Learning objectives

* Explain the difference between a measurement, a target, and an agreement.
* Trace the 2 evidence paths through SLOscope.
* Identify which infrastructure is runnable in this lab and which live components still need qualification.

== Learn: SLI, SLO, and SLA in a minute

* *SLI (service level indicator)* is what you measure. For checkout, an example is the proportion of eligible requests that succeed.
* *SLO (service level objective)* is the target for that indicator over a stated period. "At least 99.9% of eligible checkout requests succeed over 30 days" is an illustrative objective, not a target chosen for this lab.
* *SLA (service level agreement)* is the commitment agreed with a customer or user, including the consequences or remedy if the agreed service level is missed. Generating a threshold does not create or amend that agreement.

Remember: *measure, aim, agree*. An SLI tells you what happened; an SLO states the reliability you are aiming for; an SLA adds the agreement with the user. The owner must choose the useful indicator, evaluation period, and target before deciding whether an objective was missed.

== Show: Put the terms into the checkout decision

The reference contains 230 errors among 100000 requests. Its error ratio is 0.0023, or 0.23%. Under this fixture's definition, success is the complement: 99.77%. Those are measured indicators, not an objective or a customer agreement.

If someone asks, "Did we break the SLA?", those counts alone are insufficient. You need the applicable agreement, the definition of eligible requests and success, and its evaluation period. The illustrative 99.9% objective above must not be applied to an unmatched fixture window as if it were an approved commitment.

Similarly, SLOscope's proposal schema uses `slo_target` and `sla_target` as numerical fields. Treat the latter as a proposed threshold in a review artifact. It is not evidence of a negotiated agreement, a remedy, or commercial approval.

== Learn: How SLOscope turns evidence into a review

There are 2 related paths. The *target-review path* computes a baseline from telemetry and can ask a model to propose targets against that baseline. The *drift-review path* compares a later window with the preserved baseline and checks the resulting signal before optional model interpretation.

image::sloscope-event-flow.svg[Event flow showing baseline and later-window paths converging at human review before export preview,link=self,window=blank,width=1100,title="Evidence flow and human decision boundary"]

. *Collect and identify evidence.* In a live environment, the Go collector reads configured telemetry. Here, a fixture supplies explicitly synthetic evidence, including service, namespace, window, counts, and reported coverage.
. *Calculate and preserve a reference.* Deterministic code computes indicators. The learner workflow freezes the baseline and records its digest so a later comparison cannot silently redefine normal.
. *Compare a changed window.* The drift engine calculates deviations and tolerance-band breaches. A breach means the observation crossed that comparison band. It does not by itself prove an SLO violation or a root cause.
. *Apply evidence constraints.* Identity, coverage, finite numbers, and consistency matter. Inadequate or conflicting input produces abstention. Admissible input can proceed to interpretation, but acceptance does not establish that a causal explanation is true.
. *Review the interpretation or target.* Optional live model calls provide advisory classifications or proposals. The core training path uses deterministic review and separately identified recorded examples; it makes no real model calls.
. *Choose a next step.* A human reviews the evidence and business context. A qualified histogram boundary can produce an export preview. Deployment, target approval, customer commitments, and operational action remain separate decisions.

The distinction matters during a promotion review: changing the baseline could hide deterioration, while exporting a syntactically valid rule could create an alert that has never been tested against real traffic.

== Show: Infrastructure and trust boundaries

The top panel is the runnable training arrangement. RHDP hosting and terminal provisioning are still being developed. The lower panel is the proposed live extension, not an environment claimed to be deployed or accepted.

image::sloscope-infrastructure.svg[Infrastructure diagram separating the runnable synthetic terminal workspace and optional local MCP process from proposed OpenShift telemetry, model endpoint, and artifact storage,link=self,window=blank,width=1100,title="Training workspace and proposed RHDP live infrastructure"]

* *Learner experience:* Classic Showroom serves the guide; the terminal runs pinned Python source in an isolated workspace. The OpenShift console tab supports the intended RHDP environment, but the core exercises do not log in to a cluster.
* *Runnable training components:* the baseline and drift engine, local evidence files, and in-process API checks. A test client calls the HTTP handlers for boundary exercises; that does not mean a production API service is running.
* *Optional integration:* an MCP client sends inline JSON to a separate local stdio server process, which invokes the same engine checks. It does not query telemetry, call a model, read arbitrary paths, or deploy anything.
* *Proposed live components:* a monitored sample service, Prometheus/Thanos, the SLOscope collector/API, a supported model endpoint, and artifact storage. OpenShift topology, permissions, access controls, model secrets, image digest, storage, and cleanup still need implementation and review.

Public source and package downloads are setup/build dependencies. They are not customer telemetry destinations in the core exercises. A real deployment also needs an explicit decision about which telemetry may be sent to its chosen model endpoint.

== Do: Trace 1 decision before touching the terminal

Suppose a later bundle reports more errors, but its coverage is below the configured policy. Choose the next step: export a new alert, ask a model for a more confident explanation, or obtain adequate evidence.

=== Verify

The appropriate next step is to obtain or repair evidence. Trace that route on the event diagram: the input reaches the constraints, the review abstains, and no new operational authority follows. A model connection or an export command cannot fill the measurement gap.

Then point to the infrastructure component you would need for a real telemetry comparison. Prometheus/Thanos and its scoped read path belong to the proposed live extension; running a local synthetic exercise does not validate that connection.

== Take away

You now have a map for the investigation: define the user concern, identify the indicator, compare suitable evidence, inspect the constraint result, and give the owner a bounded recommendation. Continue to xref:02-details.adoc[prepare the workspace], then apply that method to the checkout scenario.

== Learning outcomes

You should now understand the role of each reliability term, how the baseline and drift paths meet at human review, and why runnable training tools and a qualified live service are different delivery milestones.
